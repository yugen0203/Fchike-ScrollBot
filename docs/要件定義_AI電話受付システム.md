# 要件定義書：AI電話受付システム（株式会社 Rion Lab Japan）

- 文書バージョン: v1.0（ドラフト）
- 作成日: 2026-06-02
- 対象: Twilio + 音声AI による「不在時の一次対応・用件吸い上げ・Slack通知」システム
- ステータス: **要件定義段階**（本フェーズの成果物は本ドキュメントのみ。実装は次フェーズ）

---

## 1. 背景・目的

- 代表番号にかかってくる電話を、担当者不在でも取りこぼさず一次対応したい。
- 「人間と区別がつかないレベル」の自然な音声AIで、**定型応答だけでなく相手の用件に合わせて柔軟に**対応する。
- 通話後に「相手先名・電話番号・用件」を社内 Slack（RionLab ワークスペースの専用チャンネル）へ自動共有する。
- **電話の本数は多くない**想定のため、**ランニングコストを極力低く**抑える（従量課金中心の構成）。

### ゴール（達成できたと言える状態）
1. 050 で始まる番号に着信 → 録音告知アナウンス → AIが応対。
2. AIが用件に応じて会話し、「折り返す旨」を**可変的に**伝え、必要情報（名前・電話番号・用件）を聞き取る。
3. 通話終了後、Slack の指定チャンネルに「相手先名／電話番号／用件」が投稿される。
4. 月額の固定費・従量費がいずれも低水準に収まる。

### 非ゴール（今回やらないこと）
- 発信（アウトバウンド架電）の自動化。※折り返しは人間が行う前提。
- 予約システム・CRM との双方向連携（将来拡張候補）。
- 複数言語対応（まずは日本語のみ）。

## 2. 全体コールフロー

```
[発信者] 050番号へ着信
   │
   ▼
[Twilio] 着信を受け、Webhookサーバーへ通知
   │
   ▼
①録音告知アナウンス（AI音声 / 録音再生）
   「株式会社Rion Lab Japanです。こちらのお電話は品質向上のため録音させていただきます。」
   │
   ▼
②AI受付開始（双方向の自然会話）
   「はい。株式会社Rion Lab Japanでございます。ご予約をお伺いできますか？」
   │  ← 発信者の発話を逐次認識（STT）
   │  ← LLMが用件を理解し、可変的に応答（TTS）
   │
   ▼
③用件吸い上げ＋折り返し案内（可変）
   「承知しました。現在担当者が不在ですので折り返しご連絡いたします。
     お電話番号とお名前を頂戴できますでしょうか？」
   ・名前 / 電話番号 / 用件 を聞き取り、復唱確認
   │
   ▼
④通話終了
   │
   ▼
[サーバー] 会話ログをLLMで要約・構造化
   │
   ▼
[Slack] 指定チャンネルへ投稿
   ・相手先名 / 電話番号 / 用件（＋日時・通話時間・録音リンク等）
```

## 3. 機能要件（FR）

| ID | 要件 | 詳細 |
|----|------|------|
| FR-1 | 050番号の取得・着信受付 | Twilio で 050（IP電話）番号を取得し、インバウンド着信を受ける。 |
| FR-2 | 録音告知アナウンス | 通話冒頭で会社名＋録音告知を再生（固定文言、AI音声 or 事前生成音声）。 |
| FR-3 | AI一次応対 | 自然な日本語音声でAIが応対を開始する。 |
| FR-4 | 可変対応（用件理解） | 予約に限らず、問い合わせ・営業・取次依頼など**用件に応じて応答を変える**。 |
| FR-5 | 折り返し案内（可変） | 担当者不在→折り返しの旨を、用件・状況に合わせた言い回しで伝える。 |
| FR-6 | 情報聞き取り | 相手先名・電話番号を聞き取り、**復唱して確認**する。発信者番号(CallerID)が取得できる場合は補完に使う。 |
| FR-7 | 用件の要約・構造化 | 通話内容をLLMで要約し、「名前／電話番号／用件」を構造化する。 |
| FR-8 | Slack通知 | 通話終了後、指定チャンネルへ整形して投稿する。 |
| FR-9 | 通話録音（任意） | 「品質向上のため」録音を保存。録音リンクをSlackに添付可能にする。 |
| FR-10 | フォールバック | AIが聞き取れない／無言が続く場合の再質問・終話処理を行う。 |

### 3.1 会話設計の方針（FR-4 / FR-5）
- LLM（GPTなど）に**システムプロンプトで役割・口調・制約・聞き取り必須項目**を与え、シナリオ分岐をハードコードせず自然対話で処理する。
- 必須収集項目（名前・電話番号・用件）が**揃うまで**会話を継続。揃ったら復唱確認→終話。
- 強い営業・無言・いたずら・緊急対応など想定外パターンの簡易ガードを用意（後述リスク参照）。

## 4. 非機能要件（NFR）

| 区分 | 要件 |
|------|------|
| 音声品質 | 抑揚・間・イントネーションが自然で、可能な限り人間と区別しにくいこと。※**フェーズ0で実サンプルを生成し評価**して最終決定。 |
| 応答遅延 | 発話に対する応答開始まで概ね1〜2秒以内を目標（リアルタイム性重視）。 |
| 可用性 | 着信を取りこぼさないため、Webhookサーバーは常時起動。障害時は留守電/転送にフォールバック可能にする。 |
| コスト | 固定費を最小化し従量課金中心に。低コール量で**月数千円以内**を目標。 |
| セキュリティ | APIキー等は環境変数/シークレット管理。録音・個人情報のアクセス制限。 |
| コンプライアンス | 録音告知の実施、個人情報の適切な取り扱い、Twilio本人確認(規制要件)の遵守。 |
| 保守性 | 文言・プロンプト・通知フォーマットを設定で変更しやすくする。 |

## 5. システム構成（アーキテクチャ）

```
                ┌──────────────┐
   PSTN/IP網 →  │   Twilio      │  ← 050番号 / 着信 / 録音 / メディアストリーム
                └──────┬───────┘
                       │ Webhook(HTTPS) + 双方向音声(WebSocket)
                       ▼
        ┌────────────────────────────────┐
        │  Webhookサーバー（常時起動・軽量）   │  例: Fly.io / Render
        │  - 着信ハンドリング(TwiML)          │
        │  - アナウンス再生制御                │
        │  - 音声AIブリッジ(STT/LLM/TTS)      │
        │  - 会話要約・構造化                  │
        └───────┬───────────────┬─────────┘
                │               │
                ▼               ▼
        ┌─────────────┐   ┌──────────────┐
        │ 音声AI/LLM   │   │   Slack       │
        │ (下記候補)    │   │ Incoming Webhook│
        └─────────────┘   └──────────────┘
```

### 音声処理の実現方式（2案）
- **案A：Twilio ConversationRelay + ElevenLabs音声 + GPT（推奨の品質寄り）**
  Twilio がSTT/TTSと音声ストリームを仲介し、TTSに ElevenLabs（日本語の抑揚が最も人間に近い）を採用。会話の頭脳はGPT。
- **案B：OpenAI Realtime API（音声→音声・最安/低遅延）**
  単一APIで音声入出力。実装がシンプルで安価・低遅延。音声は十分自然だが、ElevenLabsよりわずかにAIらしさが残る場合あり。

> いずれも**フェーズ0で本番に近い文言のサンプル音声を生成して比較**し、最終採用を決定する。

## 6. 技術スタック（候補）

| レイヤ | 採用候補 | 備考 |
|--------|----------|------|
| 電話番号/通話 | **Twilio**（050番号 / Programmable Voice） | 本人確認(Regulatory Bundle)が必要・開通約2営業日。 |
| 音声合成(TTS) | **ElevenLabs**（案A） | 日本語の抑揚・自然さが高評価。 |
| 音声対話(統合) | **OpenAI Realtime API**（案B） | 音声→音声、低遅延・低コスト。 |
| 言語モデル(LLM) | GPT系（例: gpt-4o / gpt-4o-mini） | 用件理解・要約・構造化。 |
| 実装言語 | Python（既存リポジトリに準拠） | サーバーは FastAPI 等を想定。 |
| ホスティング | Fly.io / Render 等の常時起動軽量環境 | WebSocket常時接続に対応・低月額。 |
| 通知 | Slack Incoming Webhook | 指定チャンネルへ投稿。 |
| シークレット管理 | 環境変数 / ホスティングのSecrets | APIキーをコードに含めない。 |

## 7. 会話シナリオ／文言（本番に近いサンプル）

### 7.1 録音告知（固定・FR-2）
> 「株式会社Rion Lab Japanです。こちらのお電話は品質向上のため録音させていただきます。」

### 7.2 AI受付の開始（FR-3）
> 「はい。株式会社Rion Lab Japanでございます。ご予約をお伺いできますか？」

### 7.3 用件ヒアリング後の折り返し案内（可変・FR-5）
> 「承知しました。あいにく現在担当者が不在ですので、折り返しご連絡させていただきます。
> お電話番号とお名前を頂戴できますでしょうか？」

### 7.4 復唱確認（FR-6）
> 「ありがとうございます。〇〇様、お電話番号は 0X0-XXXX-XXXX、ご用件は△△ で承りました。
> 担当者より折り返しご連絡いたします。本日はお電話ありがとうございました。」

### 7.5 システムプロンプト要旨（LLMへの指示・FR-4）
- あなたは「株式会社Rion Lab Japan」の丁寧で自然な電話受付担当。
- 目的：①用件を理解し、②担当者不在のため折り返す旨を状況に応じた言い回しで伝え、③**名前・電話番号・用件**を確実に聞き取って復唱確認する。
- 予約に限らずあらゆる用件に対応。わからない点は確認質問をする。
- 必須3項目が揃うまで会話を続け、揃ったら復唱→丁寧に終話。
- 営業電話・いたずら・緊急時の簡易対応ルールを持つ（後述）。

> ※フェーズ0の音声サンプルは、上記 7.1〜7.4 の文言で生成・試聴する。

## 10. 法令・コンプライアンス

- **録音告知**：通話冒頭で録音する旨を必ず案内（FR-2で担保）。
- **Twilio 本人確認（Regulatory Bundle）**：日本の050番号取得には法人確認書類（登記事項証明書、住所等）の提出が必須。開通まで約2営業日。
- **個人情報保護**：聞き取った氏名・電話番号・録音は最小限の範囲で保管し、アクセスを制限。保存期間・削除方針を定める。
- **AI応対の明示（任意検討）**：相手にAIが応対している旨を伝えるかは運用方針として要決定。
- **Slack共有範囲**：個人情報を含むため、チャンネルの参加メンバー範囲を限定する。

## 13. リスク・留意点

- **音声品質の主観差**：人間らしさは主観に依存。フェーズ0の試聴で必ず合意形成する。
- **本人確認の所要日数**：番号開通に約2営業日。スケジュールに織り込む。
- **非通知着信**：CallerIDが取れないケースがあるため、電話番号は会話で必ず聞き取る。
- **聞き間違い**：電話番号・氏名は復唱確認で精度を担保。漢字表記までは確定できない点に留意。
- **遅延/通話品質**：ネットワークや海外API経由のレイテンシ。リージョン選定で緩和。
- **想定外発話**：営業電話・無言・長時間・緊急（救急/事故等）対応の方針を定義する必要。
- **コスト増**：コール量増加や長時間通話で従量費が増える。上限アラート設定を検討。
- **AI誤応答**：誤った約束（料金提示・確約など）をしないようプロンプトで制約。
